# Архитектура Workflow

## Фоновые профессии — согласованная цель

[Контракт профессий](background-professions.md) расширяет существующий движок
исследованиями проекта без предварительной Tracker Task. Fleet владеет процессами,
расписаниями, находками и сессиями; Workflow — фазами и отчётами. Нельзя объявлять
старый локальный Bug Search search/verification реализацией новой модели или
создавать фиктивную задачу для admission. Source, активация и live-приёмка различаются.

## Поддерживаемые Режимы

`PROJECT_WORKFLOW_MODE=platform|standalone` выбирает допуск к операции, не другой
Advisor или формат отчёта. Default — platform; отсутствие зависимости не включает
запасной путь. Platform использует Auth/Tracker identity, assignment и отдельное
подтверждение требований владельцем у PM. Standalone использует собственную PostgreSQL без
Auth/Fleet/Tracker. Прямой сервер и опубликованный Compose-порт ограничены loopback;
не публиковать standalone через внешний ingress. Платформенные ownership,
execution contexts и assignments запрещают запуск такой БД без авторизации.
Прямой запуск проверяет loopback bind и peer, forwarded headers не считаются
доказательством. Только контейнерная поставка явно включает
`PROJECT_WORKFLOW_STANDALONE_CONTAINER_NETWORK=true`: приватная Compose-сеть
является границей доверия, host port публикуется исключительно на loopback.
Этот параметр нельзя включать для прямого запуска или внешнего ingress.
В platform Auth проверяет credential и подтверждает личность, активную учётную
запись, роль и срок действия. Отдельный application_access grant для использования
Workflow не требуется. Это не расширяет предметные права: namespace/project/task
access, ограничения технических токенов, административная роль и отдельное
подтверждение владельца проверяются на своих границах. Standalone не использует
Auth и не включается после его отказа.

Обе команды идут через `POST /internal/runtime/step` и `GET /internal/runtime/history`.
Для локального старта явно задаются task, namespace, workflow, mode и operation key
(`step --start`). Обычный step не создаёт отсутствующую задачу. Старт и оценки
используют существующие таблицы assignments/history, без внешних вымышленных
identities. Локальное завершение не выдаёт Tracker receipt или owner confirmation.

На новый валидный отчёт выполняется один модельный вызов. Parser проверяет JSON,
но не исправляет смысл. Невалидный ответ, timeout и транспортный отказ сохраняются
как технический результат, без продвижения и автоматического повтора. Readback/replay
не вызывают модель и не изменяют cursor. Оценка и переход сохраняются атомарно.

Агент собирает отчёт как объект и сериализует стандартной JSON-библиотекой;
`source`, `result`, `unresolved` находятся на одном уровне. Документ берётся из
разобранного readback без перепечатывания. Локальная ошибка формата означает,
что отчёт не отправлен и Advisor не вызван. Ошибка сообщает безопасную причину,
позицию синтаксического отказа либо путь объявленного поля и ожидаемый тип,
но не выводит содержимое документа и не угадывает исправление JSON. Неизвестный
сетевой исход требует readback исходной операции, а не новой отправки.

Ожидание модели — 1200 секунд, connect — 30, CLI read — 1500. Внешние исполнители
и ingress не должны сокращать бюджет. Socket timeout не гарантирует суммарный
wall-clock SLA. Health/Auth/Tracker проверки доступности сохраняют короткие бюджеты.

Эти значения и остальные настройки model/provider, reasoning, token budgets,
retry/transport/security policy принадлежат приложению. У исполнителя нет
соответствующих полей в отчёте, рабочем API или Workflow CLI; инструкция агента
не должна учить подбирать их. DTO отклоняет неизвестные поля до оценки, клиент
и Advisor используют подготовленную конфигурацию. Содержимое бизнес-артефакта,
например требование к таймауту разрабатываемого продукта, остаётся данными;
оно не интерпретируется как настройка проверяющего.

Граница terminal внешнего runtime проверяется отдельно: SDLC-41 передал
`terminal.timeout=30`, который внешний исполнитель применил вместо настроенного значения.
Его default не фиксирует значение от override. Действующий Workflow API этого
поля не принимал; HTTP/JSON schema Advisor не была источником короткого ожидания.
По явному решению владельца исходники внешнего исполнителя не меняются. Для всех профессий
используется одна общая инструкция терминала и заранее подготовленная конфигурация
приложения, а не выбор короткого ожидания для каждого вызова. Поле внешнего
инструмента остаётся технически доступным: инструкция не является принудительным
запретом. Это заявленная граница стороннего исполнителя, не ожидающий установки
патч внешнего исполнителя. При произвольном shell также не заявляется изоляция конфигурации.

Workflow по умолчанию не ограничивает генерацию Advisor дополнительным числом:
`max_output_tokens` отсутствует в запросе. Необязательный `OPENAI_MAX_TOKENS`
применяется только при явной настройке оператора; пустое значение не устанавливает
потолок. Это не обещание бесконечного ответа: пределы модели/провайдера сохраняются.
В reasoning-модели лимит генерации включает и reasoning, поэтому длина видимого
JSON не обосновывает малый бюджет. Незавершённый ответ остаётся техническим отказом,
не дополняется сервером и не повторяется автоматически.

Входной отчёт не ограничивается произвольным числом символов. CLI читает весь
stdin; API, хранение и Advisor сохраняют структуру и полное содержимое документов.
Пределы транспорта, памяти и провайдера отделены от предметного контракта:
они требуют конкретного основания и явного отказа, а не скрытого усечения.
Новый ограничитель на этой цепочке требует граничной проверки целостности и
документированной причины. Размер страницы history и диагностического preview
не ограничивает историю текущей фазы, отправляемую Advisor.

Старые отчёты и применённые миграции сохраняются, но текстовые старые отметки
не участвуют в новом covered. Удаление workflow требует явного переназначения
namespaces. Недоступный каталог сервисов не создаёт статических ссылок.
Фактический статус release gates фиксируется отдельно в CHANGELOG.

Workflow ведёт агента по сохранённым фазам: возвращает инструкции, принимает
отчёт, оценивает его через advisor и сохраняет результат и историю. Один
[configured-cli-v1](configured-cli-v1.md) обслуживает семь профессий и восемь
режимов, включая Developer initial/rework.

## Ответственность

| Компонент | Владеет |
| --- | --- |
| Workflow | Каталог инструкций, фазы, оценка отчётов и история |
| Tracker | Задача, требования, назначение, комментарии, стадия и статус |
| Fleet | Конфигурация, доставка сообщений и фактическое исполнение агента |
| Base | Общий CLI-транспорт, упаковка и канонические инструкции |
| Central Auth | Учётные записи, служебные PAT и браузерные сессии |

Разделены три области ответственности:

1. Общие для всех агентов: работа через Workflow CLI, фактические доказательства,
   readback неизвестного исхода и правила повторов. Канонический пакет принадлежит
   [Base agent-skills](https://github.com/FerrPOINT/services-base/blob/f8e375c08ad9ecbc3da1adcf227f2ff827c7a65d/agent-skills/README.md#инструкции-и-workflow).
2. Специфичные для профессии: её обязанности, инструкции и необходимые навыки.
3. Независимо настроенный Workflow: порядок фаз, инструкции текущей фазы,
   checks и evidence. Этот маршрут не зашивается в роль или skill.

Skills объясняют, как пользоваться инструментами, но не определяют бизнес-маршрут.
Права, назначения и переходы проверяет сервер; инструкции и skills не дают
полномочий. Критерии для Advisor задаёт текущий Workflow, не роль или skill.

Общая основа Base — project-workflow-executor, tracker-operator и
immutable-evidence-reporting. PM role описывает бизнес-уточнения, качество документа
и согласие владельца; requirements-analysis — предметный метод PM/Analyst, без
исследовательского процесса Analyst. Карта выше ссылается на source-версию,
не переключает consumer pin или инструкции уже начатого исполнения.

Каталог инструкций является данными сервера, а не версией CLI-протокола.
При неизменных командах, DTO и режимах текстовая правка не требует обновления
проверенного совместимого CLI, управляющего сервиса или исполняющего агента.
CLI сохраняет проверки
формата, protocol и identity; допустимость конкретного профиля проверяет сервер.
Совместимость клиента подтверждается отдельно от публикации нового текста.
Технические readbacks нужны для сверки назначения, но их envelope, служебные ID
и counters не копируются в содержательный отчёт Advisor.

Требуемые навыки исполнителя определяются полями skills выбранной опубликованной
редакции Workflow. Существующий внутренний namespace-binding response возвращает
их объединение в required_skills рядом с неизменным binding. Этот список —
метаданные подготовки, не новое разрешение или часть authority/fingerprint.
Fleet проверяет наличие enabled/nonempty skills с точными именами в snapshot;
содержимым владеет Base. Независимого списка обязательных defaults у single-task
профиля нет. Отсутствующий список — техническая несовместимость; явный пустой
список означает, что выбранные фазы не требуют skills, а не выбор старого пути.

Конфигурация и файлы устанавливаются явно между запусками. Исполнитель читает
перечисленные phase_contract.skills из своего настроенного каталога через terminal.
Для этого не нужны новые инструменты, aliases, автоматическая установка или
загрузка всех skill bodies в prompt. Skill — инструкция, не доказательство
выполнения команды: отказ в прошлом не является результатом новой попытки.
Worker-инструкция чтения файлов не добавляется в запрос Advisor. Исторические
binding/snapshots остаются неизменными; обновление producer и consumer согласуется
до новых запусков, без автоматического fallback на отсутствующие метаданные.

Физическая конфигурация и фактически сохранённый prompt resumed native session —
разные доказательства. Native storage может хранить prompt по hash при raw
system_prompt=NULL: для аудита требуется разрешить hash в сохранённый snapshot.
Установка новых файлов/SOUL не доказывает обновление уже существующей session.
Поддерживаемого native in-place refresh API с сохранением context/history в
проверенном комплекте нет; Workflow не добавляет такой механизм, aliases,
скрытую ротацию session или прямую правку native БД.

### Самостоятельные Analyst И Architect

PM уточняет требования и получает exact-revision consent владельца; Analyst и
Architect не повторяют опрос и не ждут согласования. Бизнес-противоречия и
недостающие решения трактуют самостоятельно с decision log в той же Task по
общему project-workflow-executor. Предположения не становятся проверенными
фактами; исходные требования, owner consent и история не переписываются.
Права, доступ к обязательным источникам и доказательства действий сохраняются.

Architect читает закреплённые исходники по canonical forge-operator, без
обязательного pipeline, checkout или Task workspace. Новый design result
ссылается на точную сохранённую decomposition revision и её content_sha256;
attachment не заменяет structured plan. Это source-контракт: доставка skill,
selected required_skills, конфигурация и установленный API проверяются отдельно.
Новый source default не заменяет уже выбранные публикации и execution snapshots;
baseline852 и registered0031 сохранены для точного исторического чтения/перехода.

## Стадия, Статус И Завершение Исполнения

Согласованный переход Start/Completed использует обычные публикации каталога.
Registered0031 добавляет новый исходный baseline, сохраняя прежние редакции,
привязки и отчёты. Если выбрана операторская редакция, перед установкой оператор
явно публикует полный принятый target через существующий API между запусками;
миграция проверяет точное равенство содержимого, не сливает его эвристиками.
Любое другое custom-содержимое блокирует обновление до записей. Архивный readback
не является допуском нового исполнения и не требует повторной оценки.

Это три разных состояния, а не три названия одного поля:

- Стадия Tracker определяет этап задачи: Draft, Analysis, Architecture и далее.
- Статус Tracker описывает работу на этом этапе; он не выводится из ответа
  модели, runtime run status или номера фазы Workflow.
- `complete=true` Workflow означает завершение назначенного исполнения профессии.
  Завершение PM не означает завершение всей задачи.

### Целевое Правило Для Каждой Профессии

Владелец явно уточнил порядок2026-11-07; он одинаков для всех семи агентов:

1. Агент первым предметным действием устанавливает статус текущей работы
   `InProgress` штатной командой Tracker. Запуск контейнера или выдача назначения
   не подменяют это действие агента.
2. Агент выполняет фазы своего Workflow. После принятого завершения и обязательных
   предметных проверок сам устанавливает `Completed`. Для PM сохраняются полные
   требования и отдельное подтверждение владельца; технических human popup нет.
3. Приложение обрабатывает завершение именно этого назначения, выбирает следующую
   стадию по действующему процессу, сбрасывает статус в `Ready` и передаёт работу
   следующему агенту. Смена стадии и этот сброс составляют одну согласованную
   операцию. Агент,
   Advisor и текст отчёта не задают произвольную следующую стадию.
4. Следующий агент снова первым действием устанавливает `InProgress`, в конце —
   `Completed`. Приложение устанавливает `Ready` при передаче, но не `InProgress`
   или `Completed` вместо следующего агента. Последняя стадия остаётся Completed:
   если следующей стадии нет, сброса в Ready нет.

`Ready` в прежнем контракте означает ожидание начала работы, не `Completed`.
Заменять им завершение предыдущей профессии нельзя. Одно принятое завершение
разрешает только соответствующую передачу: повторная доставка либо оставшийся
`Completed` не являются завершением следующей стадии. Используются действующие
назначения, версии и защита повторов, не новая эвристика по тексту отчёта.
Завершение отдельной профессии не равно завершению всего SDLC.

Workflow не назначает следующего агента и не принимает произвольные target
stage/status от модели. Fleet доставляет сохранённое назначение, а не выбирает
бизнес-переход. Readback стадии, статуса, назначения и результата Workflow
проверяется раздельно. Техническая ошибка или неизвестный ответ не доказывают
переход; сначала читается исходная операция.

### Подтверждённые Расхождения Реализации

Правило выше не объявляется реализованным одной редактурой инструкций.
В установленном Tracker `b54f9e6c` для delivery-профессий начало `InProgress`
сейчас выполняет серверный `BindRun`; Workflow требует такой статус до первой
инструкции. У PM также нет обязательной явной первой команды Start; его статус
меняется серверной обработкой предметных команд. PM completion
отдельно сохраняет admission `completed`, но задачу и immutable receipt записывает
как `Backlog/Ready`, не как поставленный агентом `Completed`. Установку этого
статуса агентом нельзя заменить словами о завершении admission или Workflow.
Остальные профессии подают proposal; серверный Complete сейчас меняет и стадию,
и статус, а `Completed` выставляет только в конце DevOps. Требуется изменить
именно эти границы, а не переименовать их в документации.

Текущая issue-проекция считает `Completed` закрытым статусом. Перед включением
целевого перехода нужно согласованно проверить завершение текущей стадии,
передачу и завершение всего SDLC; одна текстовая замена `Ready` на `Completed`
не исправляет этот контракт. Исторические PM receipts/редакции не переписываются.
Старый Backlog/Ready — результат прежнего протокола, не целевой финал агента.
Факт последующей стадии читается отдельно, не выводится из Workflow PASS.
Текущие evidence и ограничения — в [диагнозе](ADVISOR_DIAGNOSIS_20261101.md).
Невыполнимые команды не публикуются как рабочая инструкция до исправления
соответствующих CLI/Tracker admission и проверки переходов.
Standalone без Tracker завершает только собственный Workflow; правило передачи
бизнес-задачи между агентами относится к platform.

Агент не назначает себя. Fleet передаёт проверенное назначение через существующий
`POST /internal/runtime/assign`. Workflow сверяет текущий контекст Tracker,
служебную identity, профессию, выбранный workflow и режим. Назначение создаёт
или продолжает сохранённое исполнение; чтение `step` не создаёт бизнес-задачу.

## Путь исполнения

1. URL, служебный PAT и идентификаторы настраиваются у агента заранее.
2. `project-workflow --json step --task <key>` возвращает текущую фазу и версию.
3. Агент выполняет инструкции и подаёт фактический отчёт на stdin `step --report -`
   со стабильным ключом операции и ожидаемой версией.
4. Workflow оценивает отчёт через настроенную модель. Перед commit повторно
   проверяются назначение, права, версия и принадлежность workflow профессии.
5. `history` читает сохранённые отчёты и ответы. Повтор той же операции возвращает
   исходный результат; изменённое тело с тем же ключом конфликтует.

CLI использует общий HTTP-клиент Base. Ошибка HTTP не включает прямую запись
в локальную БД, файловый bootstrap или скрытый повтор. При неизвестном результате
записи агент читает `history --operation-key` исходной операции.

Профессия содержит коллекцию workflow. Сохранённая задача ссылается на профессию
и конкретный workflow независимо от прежнего дефолта. Удаление workflow из
коллекции запрещает дальнейшее исполнение, сохраняя авторизованное чтение истории.
Миграции и уже опубликованные идентификаторы и отчёты сохраняются.

Проверка допуска новой публикации выполняется при сохранении draft и новом
publish, не при чтении уже принятой редакции. Readback сверяет receipt с точными
строками сохранённого содержимого и сохраняет trusted mode identity/scopes,
роль, execution restrictions и выбранный указатель. Более поздние количества
инструкций/checks не переоценивают историческую публикацию. Exact replay не
переключает указатель назад и не создаёт новое разрешение.

## Граница Advisor

Единственный транспорт Advisor — native Responses со строгой `text.format`:
без преобразования Chat Completions, выбора JSON mode и автоматического повтора.
Сохраняются текущая политика v19, reasoning high, модель и бюджет ответа.
Схема строится из того же множества критериев, которое проверяет сервер.
HTTP200, корректный JSON и provider metadata не подтверждают соблюдение схемы.
Перед смысловой квалификацией нужны маршрутные проверки фактических ограничений;
если они не проходят, установка блокируется без автоматического downgrade.
Даже подтверждённая строгая схема не заменяет локальную проверку согласованности
полей и независимую проверку смысла. Нельзя объявлять применёнными upstream
reasoning или лимиты только по параметрам исходящего запроса Workflow.

Действующий контракт v19 типизирован:
`source:{request,decisions:[{subject,value}]}`,
`result:{artifacts:[{name,content}],assumptions:string[]}`,
`unresolved:[{kind:question|obstacle,text}]`. Поля обязательны, типы строгие;
содержимое артефакта и значение решения остаются данными без схем профессий.
Агент сохраняет нужные действующие исходные решения и полный фактический результат;
дополнение не является способом потерять прежние существенные факты. Документы
остаются данными, а не инструкциями проверяющему.

Prompt, builder, схема ответа и parser общие для всех профессий и для standalone.
Платформенный каталог содержит семь профессий и восемь режимов, включая Developer
initial/rework; standalone использует явно выбранные локальные workflow и фазы.
Различаются критерии и серверные предметные ограничения, не механизм оценки.
Проверка всех режимов с контролируемым HTTP-провайдером подтверждает механику,
но не заменяет приёмку качества ответов модели и реальных результатов профессий.

Advisor получает название фазы, допустимые решения, критерии с локальными C/E
обозначениями, последнюю оценку рядом с каждым критерием, предыдущие отчёты только
той же задачи, текущей фазы/группы, режима и цикла, затем текущий отчёт.
История передаётся по времени, без скрытого усечения и суммаризации. Прежняя
отметка не заменяет исходный факт; позднее явное изменение имеет приоритет,
отсутствие повторного упоминания не отменяет решение. Техническая ошибка не
снимает прежнюю оценку. Рабочие инструкции, весь transcript и квитанции не добавляются.
Права и точное согласование требований проверяет сервер вне model messages.
Исходная группа отчёта сохраняется до вызова модели в `evaluated_phase_group`.
Конкурентное изменение каталога не перепривязывает отчёт к новой группе;
некорректная или отсутствующая привязка даёт явную техническую ошибку.
Это серверная provenance, не дополнительный контекст Advisor.

Внутренний ответ содержит `verdict`, одну `assessment` с boolean и причиной на
каждый критерий, `required_change` (обязательное исправление для false, null для
true), `blockers` и `confidence`. Строгий parser проверяет форму,
полное множество пунктов и согласованность решения; смысл оценивает одна модель.
Сервер формирует совместимый публичный результат и не исправляет его по ключевым
словам, confidence или частным исключениям. Исторический readback не является
новой оценкой или запасным путём исполнения.
Незавершённый требуемый результат означает `PARTIAL`. Для `BLOCKED` нужно отдельно
сообщённое препятствие выполнению самой работы; неполный документ или вопрос
владельцу сами по себе не являются таким препятствием. Смысл оценивает Advisor,
а не keyword-проверка или флаг `unresolved.kind` в серверном коде.

При техническом отказе сохраняются диагностика и прежнее покрытие, продвижения
нет. Предыдущие covered — оценки, не исходные факты; новое опровержение может
снять отметку. Версия политики и алгоритм отпечатка сохраняются вместе с принятым
результатом. Повторное чтение не запускает прежний или текущий prompt. Архивные
форматы не преобразуются в новые разрешения; точные raw-report receipts
проверяются одним действующим алгоритмом без исторической нормализации.
Отпечаток новых оценок включает точный контекст фазы и проверяется повторно после
модельного вызова. Он хранится только на сервере и не попадает в model messages.
Несовместимый архив в контексте новой оценки вызывает явный технический отказ;
чтение принятой истории не требует нового parser, модели или перепривязки.

Baseline PM: FLEETQA-30/31/32 завершены до Backlog/Ready; ошибки и ограничения
сохранены в [аудите](ADVISOR_AUDIT_20261103.md). Этот результат не означает приёмку
других профессий. Изменения инструкций, механики и модели сравниваются отдельно;
новый механизм наблюдаемости, шаблонов или маршрутизации для этого не нужен.

## Завершение и доступ

Принятая финальная фаза создаёт сохранённый terminal receipt и инструкции
завершения. Она сама не переводит задачу Tracker. Агент публикует итоговый
комментарий; Tracker проверяет его и сохранённый результат Workflow
server-to-server перед атомарным переходом. Последующая передача в Analysis
принадлежит Tracker и проверяется отдельно от завершения Workflow PM.
Финальный PM-отчёт требует действительного подтверждения владельцем точной
редакции требований. Он не обязан доказывать свой будущий PASS или будущий
переход Tracker. Новое решение о передаче не переписывает прежние исполнения
и не активирует новую редакцию инструкций посреди действующего запуска.

Web UI показывает каталог, фазы и историю; человеческий доступ проверяется
через Central Auth и продуктовый admission. Машинный PAT не становится
браузерной сессией. Native run ID и фактическое завершение процесса принадлежат
Fleet, а не отдельному протоколу привязки Workflow.
