# Диагностика Проверяющего

## Что Проверяется

PM сохраняет требования в Tracker. Для завершения фазы он подаёт отчёт через
Workflow CLI. Настроенная в Workflow модель advisor оценивает этот отчёт по
checks/evidence; сервер проверяет формат ответа, полномочия и переход. Это
другой вызов модели, не ответ PM в Fleet и не подтверждение владельца.

В сохранённых прогонах SDLC-22/23 обнаружены два разных случая:

- Настоящий недостаток: в исправленном отчёте исчез полный пакет документа и
  readback. Это обоснованный PARTIAL, который исправляет PM.
- Ошибка оценки: пакет уже содержит документ, редакцию/hash и нужные факты,
  но advisor требует дополнительное свидетельство, не предусмотренное контрактом.
  Независимо подтверждены шесть таких отказов в ограниченном replay v15.

Точная внутренняя причина конкретного выбора модели недоступна. Её объяснение
является проверяемым утверждением, не доказательством правильности. Проверка
reasoning_effort=medium не устранила ложные отказы; переполнение контекста не
подтверждено. Сбой не следует объявлять проблемой Hermes, сети или прав без
соответствующих данных. Новая диагностика не отключает обязательного advisor.

Ограниченная source-проверка v16 на `app-test` выполнена один раз для трёх
синтетических сохранённых случаев, без изменения Workflow или задач стенда:

- `136`: модель цитирует `same current assignment`, но объявляет назначение
  неподтверждённым и требует проверки гипотетических ошибок доступа. Контракт
  требует не скрывать фактическую ошибку, а не подтверждать отсутствие любой
  возможной ошибки. Независимый review подтверждает ложный отказ.
- `153`: полный документ заменён ссылкой на предыдущий отчёт. PARTIAL верен,
  но `check:2` и `evidence:2` ошибочно засчитаны. Перечень названий разделов
  не доказывает содержание документа; собственное пояснение модели признаёт
  отсутствие evidence, одновременно помещая его в covered.
- `163`: полный документ и описание фактического показа после подготовки есть.
  Модель зацепилась за дополнительную ссылку на начало прежнего сообщения и
  не учла уже приведённое описание. Независимый review подтверждает ложный отказ.

Во всех трёх вызовах HTTP 200, `finish_reason=stop`, вход не усечён, получены
пояснения всех критериев; 1902/2374/3327 total tokens. Это проверка полезности
диагностики, **не успешная приёмка качества advisor**. Запросы не повторялись
ради PASS. Настройка должна устранять как ложные missing, так и ложные covered,
не ослабляя требования к документу и отдельному подтверждению владельца.

Следующая проверяемая настройка — сначала сопоставлять факты и критерии,
затем формировать общий verdict. Нынешний образец JSON ставит verdict перед
пояснениями; это возможный источник преждевременного вывода, не доказанная
внутренняя причина ошибки модели. Изменение следует проверить на тех же
положительных и отрицательных случаях одним ограниченным прогоном, без
нового вызова модели для объяснения уже полученного решения и без ослабления
критериев ради PASS. Эта настройка пока не реализована и не принята live.

## Запись Решения

Для новых оценок существующий append-only `evaluation_snapshot` дополняется
`diagnostics` версии `evaluator-diagnostics-v1`. Новая таблица не нужна.

- Фактические system/user prompt и отчёт, SHA-256 исходных строк, длина,
  признаки маскирования и усечения. Хэш не означает, что усечённый или
  замаскированный текст пригоден для побайтового повторения.
- Каждая фактически выполненная попытка: исходный или корректирующий prompt,
  ответ по известным полям схемы и безопасная причина отклонения формата.
- Модель и параметры запроса, длительность, HTTP status, ответившая модель,
  finish_reason, request ID при безопасном формате, доступные числовые usage.
  Отсутствующее значение неизвестно, а не ноль.
- Итог модели, covered/missing по стабильным ID и текст критериев с явным
  признаком усечения.
  Техническая ошибка отделена от содержательного PARTIAL.
- Prompt v16 запрашивает краткое обоснование каждого пункта и точную цитату
  отчёта. Вывод показывает `found_in_captured_text`, `not_found` либо отсутствие
  цитаты. Сравнивается доступный замаскированный текст, не подлинность внешнего
  evidence. Некорректные пояснения помечаются отдельно и не изменяют приёмку
  шести основных полей вердикта. Прежние ответы без пояснений остаются валидными.

Ключи, Authorization, provider envelope, внутренние reasoning/thinking и
произвольный текст исключений не сохраняются. Активный API key и распознаваемые
credentials маскируются. Бизнес-документы остаются закрытыми проектными данными:
диагностический экспорт не предназначен для публикации в Git или общих логах.
Необычные пользовательские секреты всё равно требуют проверки перед передачей
экспорта третьим лицам. Новая запись не исправляет ретроспективно старые логи.

Запись ограничена 750000 UTF-8 байт. Усечения текстов, пропуски коллекций и
исчерпание общего бюджета обозначаются явно; отсутствие данных не равно нулю.
Ошибка диагностического capture сохраняется как `capture_failed` или ошибка
попытки, не подменяя бизнес-вердикт. Отклонённый провайдерский PASS остаётся
в попытках, а действительное техническое решение сервера показывается BLOCKED.

## Просмотр

Используется существующий `history`, без новой службы и вызова модели:

```bash
project-workflow --json history --task <workflow-task-key> --diagnostics --n 1
```

Следующая страница использует возвращённый `next_before` и существующий
`--before-history-id`. Диагностика возвращает одну запись за страницу, чтобы
сохранить ограничение ответа CLI. Обычный history и `fleet-summary-v1` не меняются.
Namespace, assignment и права проверяются так же, как для полного history;
диагностический флаг не даёт доступа к чужим исполнениям.

История без trace возвращает `availability=legacy`: доступны сохранённые отчёт,
контракт и решение, но точный запрос, параметры и неудачные попытки неизвестны.
Они не реконструируются из нынешнего prompt и не выдаются за фактически бывшие.

## Как Разбирать Отказ

1. Выбрать конкретную запись и проверить task/phase, версию prompt и контракт.
2. При технической ошибке проверить HTTP, finish_reason, usage и ошибку схемы.
   Timeout и неверный JSON не являются доказательством плохих требований.
3. При PARTIAL сопоставить missing ID с точным критерием и переданным отчётом.
   Требование вне контракта — ошибка advisor; отсутствующая часть полного
   документа — недостаток отчёта. При нехватке данных оставить вывод открытым.
4. Сохранить минимальный обезличенный положительный и отрицательный пример.
   Изменить один доказанный источник ошибки: контракт, инструкции, параметры
   либо код. Старые решения не переписывать и не превращать в PASS.
5. Проверить исправление на зафиксированном наборе. Model replay является новой
   оценкой, не воспроизведением детерминированного результата и не новой живой
   приёмкой PM. Не повторять неизменённый вызов ради удобного вердикта.

Сначала проверяются согласованные критерии и качество доступной модели; новый
слой оркестрации, ручное сопровождение каждого сообщения и отключение защиты
не являются диагностикой. Установка версии и живое подтверждение PM учитываются
отдельно от source-тестов этой функции.

## Проверенный Статус

Реализация остаётся source-only: установленный Workflow/PM не переключён.
На том же product source прошли132 настоящих PostgreSQL-теста с очисткой
собственного Compose QA, Ruff, mypy166 и OpenAPI parity. Полный non-PG прогон
дал3312 PASS,73 passing subtests,15 явных skips и coverage94.08269961977186%;
один тест справочника содержал старый список флагов. После его обновления
целевые96 Settings/diagnostic тестов проходят. Исходный failed receipt сохранён;
это составное подтверждение, не заявление об одном полностью зелёном запуске.
Browser/live установка и устранение семантических ошибок advisor этим не доказаны.
