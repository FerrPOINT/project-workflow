# Единый CLI/API Workflow

Нормативный контракт действующего пути. Исторические состояния, эксперименты и
причины отказов описываются отдельно в CHANGELOG и ADVISOR_DIAGNOSIS_20261101.md.
Этот документ не подтверждает установку или приёмку кандидата.

## Два Режима, Одно Ядро

`PROJECT_WORKFLOW_MODE=platform|standalone` выбирается явно, default — platform.
Отсутствие credentials или отказ зависимости не меняют режим.

- Platform: Auth identity, текущее назначение Tracker, права, версии и отдельное
  подтверждение владельца обязательны. Админ-консоль не участвует в исполнении.
- Standalone: собственная PostgreSQL, локальные namespace/workflow/mode/task;
  Auth/Fleet/Tracker не требуются. Локальное завершение не выдаёт Tracker receipt
  и не означает подтверждение внешнего владельца.
- Оба режима используют один формат отчёта, Advisor, проверку JSON, историю и
  атомарные переходы. CLI обращается по HTTP и никогда не открывает локальную БД.
- Сервер проверяет собственный режим. Platform-вход не включает локальный допуск.
  Платформенная БД с ownership/contexts/assignments не открывается в standalone.

Прямой standalone проверяет loopback bind и peer; forwarded headers не дают
локальных прав. Контейнерная поставка явно задаёт
`PROJECT_WORKFLOW_STANDALONE_CONTAINER_NETWORK=true`, изолированную сеть и
публикацию host-порта исключительно на loopback. Внешний ingress запрещён.

## Конфигурация До Работы

Один раз устанавливаются CLI и квалифицированный HTTP SDK Base; они не
устанавливаются вокруг сообщений. CLI producer закреплён в quality-gate.md.
SDK/UI/skills являются независимыми pins.

Для обоих режимов задаются `PROJECT_WORKFLOW_URL` и
`PROJECT_WORKFLOW_NAMESPACE_ID`. Standalone URL — только loopback; SDK вызывается
с явным `require_token=False`, без Authorization, proxy/netrc и чтения глобального
токена. Platform дополнительно требует выделенный `PROJECT_WORKFLOW_API_TOKEN`
и `FLEET_AGENT_ID`; общий чужой PAT не заменяет отсутствующий credential.

Platform human routes требуют актуальный enforced application_access от Auth.
Machine routes проверяют служебную identity, scopes, назначение и владение.
Standalone не использует Auth и не запускается автоматически после его отказа.

Advisor использует явно настроенные Base URL, key и model. Кандидат v19
квалифицируется с app-test/high/4000 и явной настройкой
`OPENAI_EVALUATOR_RESPONSE_FORMAT=json_schema`. Она должна пройти через упаковку
до фактического запроса; наличие настройки в исходниках не означает её активацию.
В Base Compose используются `SDLC_PROJECT_WORKFLOW_OPENAI_EVALUATOR_RESPONSE_FORMAT=json_schema`
и `SDLC_PROJECT_WORKFLOW_OPENAI_REASONING_EFFORT=high`: Base передаёт их серверу
как `OPENAI_*`. В собственном Compose Workflow задаются непосредственно
`OPENAI_EVALUATOR_RESPONSE_FORMAT=json_schema` и `OPENAI_REASONING_EFFORT=high`.
Это два способа установки, не последовательные слои. Base default reasoning=none
не заменяет явный high кандидата; Workflow default сам по себе его не перекрывает.
Default `json_object` не переключается автоматически после отказа schema.
4000 является настройкой Workflow, а не доказанным upstream-лимитом ответа:
проверенный ChatGPT-адаптер исключает output cap. Это не основание менять адаптер
без проверки поддержки его backend.
Model read timeout —1200 секунд, connect —30, CLI read —1500. Короткие
health/Auth/Tracker-проверки имеют отдельные бюджеты. Ни отсутствие ключа,
ни ошибка модели не выбирают другой provider.

Обычная история читает до 200 записей с полными отчётами и сохранёнными
результатами; полный внутренний snapshot не дублируется в этом ответе.
Транспортный бюджет обычного `GET history` — 64 МиБ, step и диагностической
проекции — 1 МиБ. Это явные защитные пределы, не доказанный максимальный размер
любого пользовательского каталога. Превышение возвращает ошибку, без обрезания
документов, изменения `n`, автоматического перелистывания или повторного запроса.
Серверное чтение истории текущей фазы для оценки по-прежнему не ограничено `n`.

## Две Команды

`step` без отчёта читает инструкции, контракт фазы и текущую version; отсутствующая
задача не создаётся. В platform исполнение принимается существующим
`POST /internal/runtime/assign` от проверенного назначающего сервиса.

В standalone запуск выполняется явно:

```bash
project-workflow --json step --task LOC-1 --start --workflow-id 2 --mode-key default --operation-key start-LOC-1
project-workflow --json step --task LOC-1
```

Namespace заранее задаётся окружением. Workflow и mode берутся из API, не
угадываются. Повтор старта с прежним ключом возвращает исходный результат;
изменённые параметры конфликтуют, существующая задача не сбрасывается.

Отчёт подаётся на stdin с отдельным стабильным operation key и version из ответа:

```bash
project-workflow --json step --task LOC-1 --report - --operation-key report-LOC-1-1 --expected-version 1
project-workflow --json history --task LOC-1 --operation-key report-LOC-1-1
```

HTTP-маршруты общие: `POST /internal/runtime/step` и
`GET /internal/runtime/history`. Полная схема генерируется в runtime-openapi.json.
Standalone расширяет вход step явным стартом и локальным выбором workflow/mode;
платформенный configured-cli-v1 wire сохраняется.

## Отчёт И Оценка

Отчёт — один типизированный JSON-объект. Все поля обязательны; формат одинаков
для полной работы, исправления и дополнения.

```json
{
  "source": {
    "request": "Исходный запрос",
    "decisions": [{"subject": "Доступ", "value": "Один пользователь"}]
  },
  "result": {
    "artifacts": [{"name": "Требования", "content": "Полный сохранённый документ"}],
    "assumptions": []
  },
  "unresolved": []
}
```

Decision содержит subject:string и value:JSON; artifact — name:string и
content:string|object; unresolved item — kind:question|obstacle и text:string.
Source сохраняет необходимые действующие решения, не только последнее сообщение.
Сообщённое подтверждение владельца относится к source.decisions; не заменять его
заявлением PM о готовности или отдельным техническим receipt.
Result содержит настоящий документ без скрытых изменений и обязательные
доказательства. Пустой unresolved — утверждение исполнителя, не доказательство.
Документы являются данными, а не инструкциями проверяющему.

Предел отчёта —32000 символов. Невалидные JSON, типы, повторные ключи и неизвестные
поля структурного контракта отклоняются явно. Содержимое artifact и decision value
остаётся произвольными JSON-данными. JSON не извлекается из произвольного текста, не
исправляется автоматически и не заменяется свободным текстом.

Advisor получает фазу, допустимые verdicts, критерии с локальными C/E labels,
последнюю действующую оценку рядом с каждым критерием, предыдущие отчёты
только текущей фазы/группы и текущий структурированный отчёт. Вся переписка,
инструкции исполнителю, SOUL, skills, hashes, UUID и квитанции не добавляются.
Полезное содержание документов не очищается смысловыми regex.

Модель возвращает verdict, assessments, blockers, confidence. Каждый критерий
получает covered:boolean, reason:string и required_change:string|null.
Невыполненный пункт требует конкретного достаточного исправления; выполненный —
null. Parser проверяет форму,
точное множество критериев и согласованность решения; он не исправляет смысл.
Сервер формирует канонические covered/missing/message из этих оценок.

Причина PARTIAL/BLOCKED/DELEGATE сохраняется и видна в JSON, обычном CLI и readback.
Advisor не добавляет обязательств вне критериев. Confidence не открывает переход.

## Состояние, Повторы И Ошибки

Прежние отчёты передаются по времени, без скрытого усечения, суммаризации или
восстановления фактов из отметок. История другой группы/режима/цикла не добавляется.
Несовместимый архивный отчёт текущей фазы явно блокирует новую оценку, но остаётся
доступным через history. Архив не конвертируется в новые полномочия.

- Сервер читает полную историю текущей задачи/фазы/mode/cycle. Новые оценки
  используют текущие ID и точный текст критериев; старые текстовые отметки не
  превращаются в covered. Позднее опровержение снимает отметку; технический отказ
  не отменяет ранее достигнутое покрытие.
- Новый обработчик отчёта делает один запрос модели. Автоматических форматных,
  транспортных, смысловых повторов и HTTP redirects нет. Невалидный ответ —
  технический отказ, не PARTIAL выполненной работы; продвижения нет.
- Оценка, операция и переход сохраняются атомарно. Проверки версии и допуска
  повторяются перед commit. Конкуренция не создаёт второй переход.
- Принятая операция с прежним ключом и телом возвращает сохранённый результат
  без модели. Изменённое тело с прежним ключом даёт409. History/replay не
  доприменяют переход и не восстанавливают состояние по догадке.
- Неизвестный исход обозначается как неизвестный. Сначала читать прежнюю
  операцию; отсутствие readback ещё не доказывает, что исходный запрос не в работе.
  Не создавать заменяющую задачу, другой формат или другой provider.
- Архивные исполнения читаются с прежними данными, без новой оценки. Они не
  принимаются автоматически как текущее назначение. Терминальная authority
  проверяется одним точным raw-report алгоритмом, без исторической нормализации.
- Удаление workflow с namespace-ссылками запрещено до явного переназначения.
  Недоступный каталог сервисов не подставляет статические адреса.

Этот контракт гарантирует сохранение принятых результатов, не математическую
однократность inference при произвольных конкурентных HTTP-доставках. Отдельный
планировщик или новый durable inference ledger не добавляется.

## Завершение PM И Выпуск

В platform отдельное подтверждение владельца относится к точной редакции
требований; сервер проверяет его вне Advisor. Служебные revision/hash передаются
существующими отдельными CLI-параметрами, не внутри бизнес-отчёта или model context.

Порядок: подтверждение владельца → Workflow completion → Tracker PM completion →
чтение stage=Backlog/status=Ready. Будущий переход не является условием предыдущего
Workflow PASS. Workflow не запускает Analyst и не определяет переход Tracker.

Выпуск требует проверенного образа и двух новых живых PM-сценариев на том же
агенте: полный запрос и скудная идея с замечанием/новой редакцией. Сборка, unit
test, mock, fixture screenshot и один удачный ответ модели не заменяют приёмку.
Старые планы не являются текущими блокерами. Актуальный результат и открытые
gates фиксируются один раз в CHANGELOG и существующем диагнозе.
