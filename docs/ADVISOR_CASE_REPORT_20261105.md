## Исторический Итог До Уточнения Набора

- Подтверждённый дефект передачи schema находился в адаптере LiteLLM; исправление уже установлено на Octo.
- Недостаточное исправление C3 в первом эксперименте v19 подтверждено отдельно; конечная инструкция требует исправления, удовлетворяющего тому же критерию.
- Исторический E2 остаётся вопросом достаточности account. Исходное замечание о trimming неоднозначно. Одну доказанную внутреннюю причину всех ответов установить не удалось.
- Четыре новых контрфактуальных контроля дали 24 обоснованные отметки и шесть достаточных в контексте ответов исправлений. Это не полная квалификация.
- Конечный v19 **не принят, не установлен и не влит**. В его основной серии получены 29 из 36 ответов: 28 без замечаний и один со спорным объяснением; все 134 отметки совпали с разметкой. Один начатый ответ неизвестен, шесть образцов не запускались.
- Подтверждён информационный разрыв в старом v15: решение владельца было в source отчёта 189, отсутствовало в source 190, а прежние отчёты не передавались. Текущий кандидат сохраняет эти факты через API/storage; новая регрессия проходит.
- Контроль с противоположными решениями только в истории показал CSV 2/2 PASS и JSON 2/2 PARTIAL при неизменном текущем CSV-артефакте. Полное игнорирование истории в этом тесте исключено; универсальность не доказана.
- Рабочий PM и установленный Workflow не менялись. Две новые живые PM-задачи кандидата не пройдены. Последний согласованный предел кампании 163: использовано132, семь предназначены для квалификации и24 для live. Новый этап не сделал вызовов: предварительное принятие всех29 ответов заблокировано одной неоднозначной correction.

## Проверка Допуска К Завершению Квалификации

Исполнение согласованного плана начато от7fed17cb без изменения модели, prompt,
критериев, старых входов и ответов. Два независимых read-only review повторно
сопоставили25 завершённых ответов основного журнала и четыре reused controls:
29 ответов,134 assessments,30 required_change и все blockers. Actual payload
совпадают с frozen inputs, literal raw совпадают с разобранными ответами.

Результат:28 ответов приняты полностью; у одного C2 reason/correction остаются
неоднозначными. Все134 marks соответствуют прежней разметке;29 corrections
приняты, одна не принята. Новых подтверждённых false PASS не найдено.

Незакрытый случай — карточка17, pm-private-access-contradiction/sample1:

- C1=false, C2=false и PARTIAL обоснованы противоречием owner-only/public edit.
- C2 дополнительно требует уточнить trimming без неподтверждённого изменения
  сохраняемых значений. Source требует непустоту после trim, но не определяет
  сохранение пробелов; Both values are trimmed не указывает этап обработки.
- Это может быть требованием убрать неоднозначность документа либо лишним
  ограничением хранения. По исходному входу нельзя однозначно принять именно
  эту correction. Это unresolved fixture/oracle issue, не доказанная ошибка
  evaluator, parser, сервера или передачи контекста.

Первоначальный условный GO одного review был отозван после проверки против
правила допуска. Оба итоговых review — NO-GO: семь успешных будущих ответов не
заменили бы приёмку старой correction. Старый gold и журнал не переписываются;
неизвестный начатый вызов остаётся учтённым расходом, не результатом.

По согласованному правилу новые вызовы, установка и merge не выполняются.
Бюджет остаётся132/163; семь квалификационных и24 live не использованы.
Артефакты native/coverage/PostgreSQL проверены по сохранённым SHA; production,
runner, Compose и constraints побайтно не менялись относительно проверенного
кода9597a52. Это reuse прежних gates, не новый полный прогон.
Новый offline preflight проходит для всех18 frozen cases/36 слотов: типы,
payload/label digests, aliases и точный production builder совпадают;
response_format=json_schema. Клиент модели не создавался, сетевых вызовов нет.

Source-only проверка упаковки подтверждает два разных способа настройки:
Base Compose принимает SDLC_PROJECT_WORKFLOW_OPENAI_EVALUATOR_RESPONSE_FORMAT
и SDLC_PROJECT_WORKFLOW_OPENAI_REASONING_EFFORT; собственный Compose Workflow
принимает OPENAI_EVALUATOR_RESPONSE_FORMAT и OPENAI_REASONING_EFFORT.
Для кандидата оба способа явно задают json_schema/high. Base default none
перекрывает Workflow default high, поэтому нельзя рассчитывать на последний.
Это подтверждённое свойство конфигурации, не установленная причина прежних
ошибок: сохранённые квалификационные запросы уже содержат high.
Обновление backend не обновляет старые CLI pins; consumer cutover остаётся
отдельным открытым gate, не основанием менять Fleet или Hermes.

Следующий необходимый шаг — отдельное решение об однозначном квалификационном
входе для этого disputed случая с сохранением прежнего результата как
непринятого. Не менять production prompt ради недоказанной ошибки и не считать
четыре контрфактуальных контроля заменой незавершённой основной серии.

Следующие разделы сохраняют хронологию расследования; прежние лимиты относятся
к моменту соответствующего этапа, не заменяют текущий предел163.

### Реальная Цепочка 189 → 190 → 191 → 192

Источник: [живой audit][LIVE], задача SDLC-32; [offline lineage proof][LINEAGE].

1. Владелец явно задал два статуса «Нужно ответить» и «Закрыта». Source189 сохранил это решение.
2. В следующем сообщении владелец подтвердил начальный статус, добавил «Жду ответа клиента» и сохранение после перезапуска. Прежнее решение о «Закрыта» не отзывал.
3. Source190 пересказал новые и часть старых условий, но пропустил «Закрыта». Фактический v15 user JSON содержит previously_covered, но не previous_reports. Старые labels не передают содержание решения владельца.
4. Ответ190 требует решение о «Закрыта», которого нет в переданном source. Его отсутствие во входе не доказывает отсутствие решения у владельца. Непереданный факт установлен сравнением переписки и точных captured inputs.
5. В191 PM вернул факт в source и clarification, а также добавил фразу в document.scope[4]. Поэтому PASS191 не является чистым однофакторным опытом.
6. Document190 точно равен сохранённому rev2. Document191 отличается только добавленной scope-фразой. Document192 снова точно равен rev2 перед подтверждённым завершением. Это исключает утверждение, будто здесь уже доказана выдача receipt на другой документ.

Точный diff документа 190→191:

- Стало: `Статусы заявки: «Нужно ответить», «Жду ответа клиента» и «Закрыта». Необходимость статуса «Закрыта» была указана владельцем в исходном запросе о статусах.`
