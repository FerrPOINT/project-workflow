# Неймспейс, набор воркфлоу и исполнение Fleet

## Модель

- Неймспейс содержит собственный набор воркфлоу. У него нет поля выбора
  или привязки к одному дефолтному воркфлоу.
- При первоначальном создании неймспейса создаётся стартовый воркфлоу
  **«Дефолтный»** по профессии неймспейса: PM, Analyst, Architect, Developer,
  Reviewer, Tester или DevOps. Это экземпляр стартового шаблона в наборе,
  а не постоянная настройка выбора воркфлоу.
- Пользователь может иметь несколько воркфлоу в одном неймспейсе.
  Фазы и инструкции каждого воркфлоу редактируются независимо.
- Конкретный воркфлоу относится к своему неймспейсу. Задача/исполнение использует
  выбранный воркфлоу этого набора; выбор не записывается как настройка неймспейса.
- Профессия определяет стартовый шаблон и профиль исполнения. Конкретный агент
  принадлежит Fleet. Реальный проект и назначения задач принадлежат Tracker.
- Таблица `projects` в Workflow остаётся историческим именем для неймспейсов.
  Новую сущность «воркфлоу проекта» не добавляем.

## Подтверждённая граница текущего кода

Текущая БД хранит `projects.workflow_id`, а составные FK задач и назначений
ограничивают неймспейс одним воркфлоу. Это противоречит модели набора;
удаление переключателя в интерфейсе не исправляет эту границу.

Старая установка пока не мигрирована. Подготовленное переименование не является
реализацией набора воркфлоу и не должно поставляться как завершение этой задачи.

## Реализация

1. Перенести владение на сторону воркфлоу: `workflows.namespace_id`.
   Убрать `projects.workflow_id` и зависимость проверок от одного воркфлоу
   неймспейса. FK задач/назначений проверяют принадлежность выбранного воркфлоу
   своему неймспейсу. Существующие ID, фазы, инструкции и историю сохранить.
2. Перенести существующие семь пар в отношение владения без пересоздания данных.
   До записи проверить неоднозначную принадлежность и незакреплённые записи;
   конфликт не исправлять удалением или перепривязкой сохранённых задач.
3. Штатная миграционная команда создаёт семь начальных неймспейсов и по одному
   стартовому «Дефолтному» по профессии. Повторный запуск не перезаписывает
   пользовательские воркфлоу, фазы или инструкции. Закреплённые шаблоны и pins
   остаются неизменными; отображаемое имя хранится в экземпляре БД.
4. В API неймспейса отдавать его набор воркфлоу и профессию. Создание/редактирование
   воркфлоу выполняется в выбранном неймспейсе. Изменение неймспейса не выбирает
   и не заменяет воркфлоу. Старый контракт Fleet/CLI сверить до смены установки;
   несовместимость не прятать фиктивным дефолтным ID или readiness-флагом.
5. В селекторах и списках неймспейсов показывать название неймспейса.
   Не добавлять название воркфлоу к нему. В редакторе неймспейса убрать выбор
   воркфлоу. Страница «Воркфлоу» показывает набор выбранного неймспейса,
   включая стартовый «Дефолтный» и пользовательские варианты.
6. Fleet получает неймспейс/профессию и проверяет выбранный воркфлоу задачи
   внутри этого набора. Назначение остаётся собственностью Tracker;
   инструкции, отчёты и история — Workflow.

## Замена исполнителя

- Hermes используется штатным: исходники и pin не менять. Продуктовую логику
  не помещать в его middleware и не связывать с приватными полями/методами.
- Общий путь агента — Fleet-owned CLI и серверные API владельцев. Конфигурация,
  запуск, транспорт, подтверждение run/session, остановка и recovery относятся
  к адаптеру Fleet. Такой же контракт требуется Java Agent.
- CLI получает машинную credential от Fleet независимо от конфигурации Hermes.
  Пользовательские credentials агенту не выдаются.
- При замене исполнителя сохраняются набор воркфлоу и история. Старый run
  сверяется/останавливается; его receipts не переносятся в другой runtime.
- Незавершённую интеграцию `fleet-sdlc` через приватные объекты Hermes не
  устанавливать. Работающий PM-путь сохраняется до проверенной замены.

## Проверка и поставка

- Новая БД: семь неймспейсов с профессиями и семь стартовых «Дефолтных».
- Заполненная БД: сохранение ID, инструкций, задач и истории при миграции.
- Два воркфлоу в одном неймспейсе: оба видны и доступны своей задаче.
- Два неймспейса со стартовыми «Дефолтными»: редактирование первого не меняет
  второй; чужой воркфлоу не назначается задаче другого неймспейса.
- Редактор неймспейса не имеет выбора воркфлоу; селекторы не смешивают названия.
- CLI и исполнитель получают фактический выбранный воркфлоу задачи, а не
  скрытую настройку неймспейса. Проверки доступа/назначения/конфигурации сохраняются.
- После одного интеграционного gate — exact source/image readback и проверка
  установленного интерфейса через Codex Browser. Старые результаты одиночной
  привязки не являются приёмкой модели набора.
