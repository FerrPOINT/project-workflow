# Неймспейс, воркфлоу и исполнение Fleet

## Модель

- У каждого технического неймспейса Workflow остаётся один дефолтный воркфлоу
  по назначению неймспейса: Developer → Developer, Reviewer → Reviewer,
  DevOps → DevOps, PM → PM и соответствующие пары остальных ролей.
  Существующие привязки и пользовательские фазы/инструкции сохраняются.
- Связь неймспейса с воркфлоу и командой CLI уже хранится в БД Workflow.
  Fleet принимает выбранный неймспейс и автоматически определяет его воркфлоу,
  роль, Hermes-профиль и CLI. Все задачи агента используют эту связку;
  режимы внутри воркфлоу сохраняются.
- Реальный проект связан с исполнителями через маршрутизацию Tracker.
  Таблица `projects` в Workflow содержит технические неймспейсы.
  Новую сущность «воркфлоу проекта» не добавляем.

## Интерфейс и настройки

1. В Workflow показывать воркфлоу выбранного неймспейса, его фазы и инструкции.
   Убрать повторный список ролей и второй переключатель воркфлоу.
2. Старые ссылки с несовпадающим `workflow_id` перенаправлять на правильную
   страницу. При сохранении проверять принадлежность фазы выбранному воркфлоу.
3. Убрать «Агенты» из основной навигации Workflow. Записи ролей и профилей
   сохранить и показывать в настройках фаз. Конкретными агентами управляет Fleet.
4. В создании и настройках Fleet заменить ручные поля namespace/workflow одним
   селектором неймспейса и информацией о полученной связке.
5. Дополнить существующий каталог Workflow сведениями о роли и профиле.
   Он уже отдаёт `workflow_id` и `cli_command`; отдельный протокол не нужен.
6. Принимать старые запросы Fleet с `workflow_id`, если он соответствует
   неймспейсу. Обновить DTO, OpenAPI и документацию.

## CLI и фактическое исполнение

1. Установить выбранный CLI в изолированное окружение агента и включить его
   в инструкции. Обёртки должны принимать корректный `--json step`.
2. Изменения привязки проводить через существующую активацию конфигурации Fleet,
   сохраняя отдельные HOME агентов и историю задач.
3. Пользовательские `/api/cli/*` сохраняют пользовательскую авторизацию.
   Машинные вызовы используют существующие runtime-механизмы и назначенную задачу.
4. Завершить необходимые проверки назначения и активной конфигурации
   в Workflow/Fleet/Tracker. Сам выбор неймспейса не подтверждает исполнение.
5. Сохранить работающий PM-путь. Готовность остальных ролей подтверждать
   фактическим выполнением; проверки не снимать, readiness-флаги не подменять.
6. Hermes остаётся закреплённым upstream: его исходники не изменять и pin
   не обновлять. CLI и интеграционный код хранить в Fleet; подключать их
   через штатные средства исполнителя в отдельном окружении агента.

## Замена исполнителя

- Tracker владеет назначением, Workflow — фазами, инструкциями, отчётами
  и историей, Fleet — привязкой назначения к конкретному исполнителю.
  Эта логика не зависит от выбора Hermes или Java Agent.
- Общий путь работы агента — установленный CLI `step`/`history` и серверный
  runtime API Fleet. Использовать штатное выполнение команд агента; при
  необходимости инструментального API — внешний MCP с тем же серверным
  контрактом. Не переносить бизнес-логику в плагины исполнителя.
- Штатный Hermes используется без патчей, monkey-patching, middleware
  с продуктовой логикой и доступа к приватным полям или методам. Его
  конфигурация, инструкции, skills и внешние инструменты задаются Fleet.
- Различия запуска, транспорта, конфигурации, подтверждения run/session,
  остановки и recovery остаются в существующих адаптерах Fleet. Их native IDs
  не становятся универсальными идентификаторами задачи или назначения.
- CLI получает машинную credential от Fleet, независимо от переменных
  конфигурации Hermes. Пользовательские credentials агенту не выдавать.
- Смена исполнителя сохраняет неймспейс, воркфлоу, инструкции и историю
  Workflow. Выполнять её после остановки/сверки текущего запуска и нового
  назначения; живой run и его receipts между runtimes не переносить.
- Проверки назначения, доступа, конфигурации и свежести сохраняются на стороне
  владельцев. Если адаптер не подтверждает нужную capability, исполнение
  блокируется с конкретной причиной; флагом готовности её не подменять.
- Новую интеграцию `fleet-sdlc`, зависящую от внутренних объектов Hermes,
  не устанавливать. Перед продолжением диспетчеризации заменить этот путь
  общим CLI и проверками адаптера. Работающий PM-путь сохраняется до отдельной
  проверенной замены; его существующая интеграция не доказывает переносимость.

## Проверка и поставка

1. Проверить сохранение всех существующих дефолтных пар неймспейс/воркфлоу
   по назначению, а также независимое редактирование двух разных неймспейсов.
2. Проверить старые ссылки, сохранение инструкций и автоматическое определение
   настроек Fleet, включая совместимость старых запросов.
3. Проверить CLI: инструкции, отчёт, историю и отказ для неназначенной задачи.
4. Выполнить сквозной сценарий: выбор неймспейса → активация конфигурации →
   запуск агента → выполнение тестовой задачи по выбранному воркфлоу.
5. После интеграционного прогона подтвердить точные установленные версии
   и интерфейс через Codex Browser. Сборку, запуск контейнера и выполнение задачи
   фиксировать отдельно.
6. Проверить неизменность исходников и закреплённого коммита Hermes.
7. Подтвердить общий CLI-контракт для Hermes и Java Agent, включая отказ
   неназначенной задаче и старому запуску. Отдельно проверить возможности
   каждого runtime-адаптера; одинаковый HTTP DTO не доказывает live-переносимость.

Порядок: сначала убрать дублирование интерфейса и ручных настроек, затем
довести CLI и назначение задачи до подтверждённого исполнения.
