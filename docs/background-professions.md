# Фоновые профессии

Статус 2026-11-09: профессии и workflow входят в штатные platform-дефолты.
Фоновое исполнение Fleet ещё не подключено.
Продуктовые требования: [Fleet — Фоновые задачи](https://github.com/FerrPOINT/fleet-control/blob/feat/background-tasks-20261108/docs/BACKGROUND_TASKS.md).

## Границы

Fleet хранит project-bound фоновые процессы, расписания, находки и отдельные сессии
исполнений. Workflow хранит обычные профессии, редактируемые определения, фазы,
инструкции, checks, evidence и отчёты. Base задаёт профессиональные инструкции и
skills, без копии последовательности фаз. Tracker получает задачу только после
явного действия человека над находкой.

Первая версия: «Поиск багов» и «Рефакторинг». Оба исследуют исходники без workspace
проекта, выполнения кода и QA-стенда. Не исправляют продукт, не создают Tracker-задачи
и не ждут уточнения человека. Это профессии вне семи стадийных SDLC-ролей; запуск
не получает вымышленную Task и не выполняется как непривязанный private chat.

Основную задачу задаёт выбранная профессия; Fleet добавляет проектный контекст и
необязательный дополнительный промпт процесса. Профиль исполнения, credentials и
model settings настраиваются до запуска обычными средствами, не рабочим отчётом.
Нет отдельного реестра агентов или назначения другого агента каждой фазе.

## Дефолтный workflow каждой профессии

| Порядок | Фаза | Проверяемый результат |
| --- | --- | --- |
| 1 | Контекст | Задача профессии и дополнительный промпт прочитаны; источники и проверенные версии определены |
| 2 | Существующие находки | Прочитаны относящиеся находки проекта, комментарии, решения и связанные задачи |
| 3 | Исследование | Кандидаты имеют основание в фактически прочитанных исходниках |
| 4 | Повторная сверка | Перед сохранением кандидаты сопоставлены с актуальными находками и человеческими решениями |
| 5 | Сохранение и отчёт | Новые находки либо дополнения сохранены; итог содержит coverage и ограничения |

У багов evidence объясняет нарушение контракта и путь ошибки по коду. У рефакторинга
evidence обосновывает конкретное упрощение и сохранение поведения. Паттерн и меньшее
число строк сами по себе не доказывают улучшение. Source-based conclusion не является
выполненным тестом. Непроверенное предположение не выдаётся за подтверждённую находку.

Каждая фаза имеет инструкции, checks и evidence в существующем формате Workflow.
Дефолты редактируются и публикуются штатно; source definition не активирует их.
Существующие исполнения и история сохраняют выбранную редакцию. Не фиксировать
число фаз исполнения технической проверкой, унаследованной от старого Bug Search.

Недостаток обязательных входов или недоступный источник завершают запуск явным
неполным/ошибочным результатом без ожидания человека. Отчёт не превращает отсутствие
проверки в «дефектов нет». Сохранение результата и terminal Workflow не означают
создание задачи или бизнес-переход Tracker.

## Работа с находками

Агенты видят разрешённые находки проекта независимо от того, какой процесс их
обнаружил. Перед исследованием читают также «Не делаем» с комментариями и связанные
Tracker-задачи. После исследования повторяют сверку с актуальными данными.

Повтор дополняет ту же находку и сохраняет правки и решения человека. Существенное
новое evidence не отменяет «Не делаем» автоматически. Возвращение проблемы после
завершённой задачи сохраняется как новое обнаружение той же находки; следующую
связанную задачу создаёт человек. Модель сопоставляет смысл, сервер обеспечивает
идентификаторы, права и защиту от повторной записи. Keyword/regex не заменяет оценку.

## Замена прежнего Bug Search и следующие версии

Локальный незавершённый preset `BUG_SEARCHER` с режимами search/verification,
авторегистрацией Bug и контрактом ровно трёх фаз не является новым дефолтом.
Его автоматическое исправление, intake и специальная перепроверка исключены.
Исторические данные и применённые миграции сохраняются; скрытый fallback к старому
исполнению не добавляется. Нужные общие части переносятся выборочно после проверки.

После появления workspace для фоновых процессов отдельно расширяется поиск багов
и добавляется «Оптимизация» — время исполнения и ресурсы. Она не создаётся сейчас.

## Подготовленные исходники

[Два дефолта](../project_workflow/references/background_professions_v1.json) содержат
пять фаз с отдельными инструкциями, checks и evidence. Явный helper
[ensure_background_professions](../project_workflow/infrastructure/db/background_professions.py)
создаёт редактируемые записи в транзакции владельца через существующие repositories.
Он вызывается штатным `python -m scripts.init_db` в platform-режиме после
семи профессий разработки. Standalone по-прежнему не заполняет каталог неявно.
Установка не создаёт Tracker Task, не активирует runtime и не добавляет
фоновые роли в семиролевой managed assignment.
Повтор сохраняет авторские изменения; конфликт со старой профессией до записи
требует явного перехода владельца и не переключается на search/verification.

Целевые SQLite tests проверили подготовку, сохранение правок и отказ без частичных
эффектов при конфликте. Существующие тесты дефолтов, scoped Ruff и mypy прошли.
В каталог Fleet передаются реальные IDs установленных фоновых профессий и
выбранных workflow; чтение каталога ничего не устанавливает. Прежняя идентичность
`BUG_SEARCHER` с другим workflow отклоняется, а не становится новым дефолтом.

2026-11-09 оба определения установлены в Workflow sdlc3 через те же repositories:
профессии/workflow 15 и 16, по пять фаз `research`, с инструкциями, checks и evidence.
Проверен реальный интерфейс. Это установка конфигурации без замены server images,
создания задач или активации расписаний. Новый расширенный runtime-каталог и
автосоздание агентов требуют установки соответствующих исходников серверов.
Background admission и сквозная runtime-приёмка остаются открытыми.

Проверка холодной установки в отдельной Compose-БД подтвердила два дефолта,
включение helper/JSON в устанавливаемый wheel, генерацию обеих namespace CLI
с реальными IDs и HTTP 200 `/health` (`database=ok`, `schema=ok`). Использован
QA-образ тех же исполняемых исходников, не замена установленного server image.
Это проверка конфигурации; выполнение фоновой профессии без Tracker-задачи
и Docker/Kubernetes-поставка ещё не квалифицированы.

## Результаты проверки 2026-11-09

Полный unit-набор на Python 3.12 дал 4824 PASS, 14 SKIP, 75 успешных subtests и
пять отказов старых fixtures: четыре зависели от глубины JSON decoder, один —
от нормализации байтов архивных отчётов Git. После точечных исправлений fixtures
все пять прошли в целевом наборе из 142 PASS вместе с регрессиями дефолтов.
Неизменённые успешные результаты переиспользованы: итоговый набор подтверждает
4829 unit-случаев; единого повторного полного прогона после fixture-правок нет.
Исполняемые деревья `project_workflow` и `scripts` совпадают в обоих прогонах.
Объединённое line coverage — 94.1352%, порог 94% сохранён.

PostgreSQL: 182 неизменённых PASS и два PASS после обновления ожидаемого общего
каталога с семи до девяти; sealed installation по-прежнему содержит семь bindings.
Включена application-clock проверка на отдельной пустой БД. Ruff и mypy
(178 source files) прошли. Временные QA-контейнеры, сети и disposable DB volumes
убраны штатным Base helper; установленный runtime не заменён.
