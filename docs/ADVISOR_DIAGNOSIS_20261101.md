Одна гипотеза, ещё не реализованная и не квалифицированная: заменить повторяющийся
блок оценки короткой универсальной связью «критерий -> нужный переданный факт ->
отметка и конкретная причина -> verdict». Проверять применимую ветку критерия;
не подменять недостающий факт другой обязанностью или собственным проектным решением.
Факт из result не становится решением в source, прежняя отметка и заявление о
полноте не заменяют исходные сведения. Итог должен следовать полученным отметкам.

Не добавлять поля, вторую модель, status-примеры, keyword-проверки, fallback или
автокоррекцию verdict. Не повышать параметры одновременно с текстом. На следующем
контролируемом сравнении проверять основания причин, а не только covered/verdict.
Нынешний эксперимент этой гипотезы не проверял; её успех не обещается заранее.

## Исторический Итоговый Анализ V14: 3 Ноября 2026

**Вывод:** новый механизм прошёл ограниченную составную модельную квалификацию,
но ещё не установлен и не принят на двух живых PM-задачах. Установленный PM
продолжает использовать прежнюю оценку. Поэтому исправление в Git нельзя выдавать
за уже исправленное поведение стенда.

### Реальная Архитектура

Проверки Auth/Tracker и назначения на сервере → контракт текущей фазы и её
последние отметки → один запрос Advisor → строгий parser → повторная проверка
состояния/полномочий → сохранение результата → причина и следующий шаг в CLI.

В модель уходят два сообщения: одна общая system-инструкция и user с названием
фазы, допустимыми решениями, критериями C/E, прежними отметками и текущим отчётом.
Builder не добавляет worker procedure, SOUL, skills, чужие фазы, внутренние ID,
hashes, квитанции или диагностику. Полный report передаётся один раз, дословно.
Нужные серверу версии и привязки остаются вне model messages. Сохранённый snapshot
с техническими реквизитами и фактический запрос модели — разные данные.

Ответ модели содержит только verdict/assessments/blockers/confidence. У каждого
критерия одна классификация и причина. Сервер детерминированно выводит прежние
covered/missing/message; точное множество, типы, дубли ключей и согласованность
verdict проверяются кодом. Валидный PARTIAL не исправляется и не повторяется до
PASS. Только неверный формат допускает один технический повтор. Timeout,
refusal, filtering и усечение не объявляются недоделанной работой PM.

### Что Ещё Не Доказано

- Чистые fixtures не гарантируют чистоту live-отчётов. Если worker пришлёт служебные
  реквизиты в report, builder не удалит их скрытым фильтром. Проверить реальный
  запрос после установленного skill необходимо в двух живых PM-сценариях.
- Marks не содержат прежних исходных фактов. Видимое противоречие снимает отметку,
  но сравнение с отсутствующим старым документом обещать нельзя. Это ограничение
  согласованного marks-only входа, не повод незаметно добавить всю переписку.
- Advisor оценивает предоставленные сведения, не доказывает истинность описанных
  действий. Права, назначение и exact owner confirmation проверяет сервер.
  Вымышленные deployment fixtures не доказывают реальное развёртывание.
- app-test — alias; upstream-модель не установлена по одному returned_model.
  Code/schema validation гарантирует форму, не правильность смыслового суждения.
  [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
  и [evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
  не заменяют проверку фактического provider route и заранее размеченных случаев.
- Developer/Reviewer представлены контекстными фазами, не всей профессиональной
  работой. Новый механизм не означает приёмку семи агентов или полного SDLC.
- Один PG clock case прошёл отдельно, но причина его раннего отказа в общем
  прогоне ещё не доказана. Нельзя объявить все release gates чистым единым прогоном.

### Минимальный Следующий Шаг

Новых слоёв и новой архитектуры не требуется. Сохранить текущий единственный
prompt/parser, закончить проверки точного кандидата и штатно доставить только
изменённый Workflow/CLI. Tester-текст активируется существующей публикацией
редакции с readback/CAS, отдельно от установки, без изменения активных запусков.
Затем два настоящих новых чата на прежнем PM: полный запрос и скудная идея с
уточнением/редакцией; самостоятельное сохранение требований, отдельное owner
confirmation и Backlog / Ready без Analyst. До этого **PM live acceptance и мерж
остаются открыты**, даже при успешной модельной матрице. Hermes/Fleet не переделывать.

### Граница Серверной Проверки И Ошибки Отчёта

`configured_cli_tracker.confirmation` читает актуальную редакцию из Tracker и
её настоящее подтверждение, сверяет задачу, владельца, revision/hash и Draft.
`configured_cli.step` сверяет с ними **поля CLI-команды**, а `finish_history`
повторяет readback перед терминальным commit. Эти проверки не зависят от PASS
модели. Авторизация и защита от смены подтверждения остаются серверными.

Однако сервер не разбирает произвольные revision/hash в тексте отчёта. В133
противоречит заголовок включённого документа; в receipt-mismatch изменён только
скопированный в report hash receipt. В model-only fixtures нет аргументов CLI;
правильные аргументы могли бы сосуществовать с ошибочным текстом. Поэтому просто
удалить сравнение всех идентификаторов значит ослабить **согласованность отчёта**,
хотя привязка настоящего подтверждения к актуальному документу останется защищена.
Предыдущее краткое объяснение «сервер уже проверяет всё это» было слишком широким.

Правильная граница: сервер гарантирует реальные права и актуальное согласие;
Advisor оценивает полноту предоставленного результата и его внутренние противоречия,
не аутентифицирует самостоятельно происхождение API или переписки. Hash не является
пользовательским бизнес-решением и не должен многократно дублироваться в критериях.
Не добавлены автоматический PASS, новый парсер report или инфраструктурный слой.

allowlist не изменена. Старые inputs/runner/results не исправляются задним числом.

**Одна следующая гипотеза:** в коротком system заменить глобальное перечисление
`actual commands/readbacks` единым правилом: формат и достаточность доказательств
определяет конкретный checks/evidence. Обязательные FULL, identity/hash, результаты,
receipt и реальные противоречия сохранить. Условие `wherever the stated items require
them` уже ограничивает прежнюю фразу, поэтому её причинное влияние не доказано;
не объявлять такую замену проверенным исправлением и не дописывать исключения под170/171.
В текущем этапе эта гипотеза **не реализована и не испытана**: лимит48 исчерпан.

Решение: сохранить опубликованную реализацию как непринятый Draft, установленный v12
не менять. Полный release gate, образ, установка, два новых чата и browser acceptance
не запускались после отказа обязательного модельного gate. Итоговый выпуск и мерж
остаются незавершёнными, а не заменяются ростом exact score.

### Избыточность, сопоставимость и неизвестное

- Worker procedure смешана с критериями результата. Собственную отправку отчёта
  нельзя доказать в этом же отчёте; system содержит исключение, но исходные команды
  остаются рядом. Для164/167 есть контролируемый эффект, для остальных переносить
  этот вывод без проверки нельзя.
- System v12 содержит общие code-regression/orphaned-artifact правила и примеры
  других профессий; их применимость к PM неочевидна. Это лишняя нагрузка контракта,
  **но причинный вклад длины/примеров отдельно не установлен**.
- Advisor повторно рассуждает о правах/receipt по изложению PM, хотя финальный сервер
  уже проверяет их. Независимо удостоверять автора каждого ответа по отсутствующему
  источнику не является оговорённой обязанностью judge. Качество документа и реальное
  согласование противоречий остаются его предметом; убрать их из проверки нельзя.
- Exact captured requests164/167/170/171 и восстановленные original-shape47 не равны:
  у последних нормализованы IDs, prior coverage пуст, delegate отсутствует, по одному
  вызову на слот против production format retries. Исторические133/153/163 не имеют
  такого же полного захвата отправленного prompt; восстановление обозначается явно.
- Masked-hash corpus исключён из оценки качества. В broad47 отдельно учитываются
  false PASS, false PARTIAL, неверные items и format errors; один агрегат exact
  не доказывает безопасность и не является production error rate.
- **Append-only QA correction:** negative B в evidence179-only trial меняет первый
  hash в171 — это receipt, а не publication/readback. Ожидание PARTIAL/check290 missing
  обосновано; ожидание evidence179 missing неоднозначно, вероятнее covered.
  Старые inputs/goldens/results не переписаны. Поэтому прежние **4/12 exact — только
  исторический score старой разметки**; 0/6 positive PASS и6/6 negative PARTIAL остаются
  наблюдениями. Уже отвергнутую дополнительную фразу evidence179 повторять не нужно.
- Полный native prompt PM, исторический backend route и скрытая причина модельной
  ошибки не установлены. Объяснения/confidence модели — её утверждения, не доказательство.
  Для зафиксированных выводов новых вызовов не потребовалось; возможность дальнейших
  различающих экспериментов не исключается.

### Один минимальный следующий пакет: контракт входа configured PM

Это предложение, **не выполненное изменение и не принятая новая политика**.

1. Только configured PM с явными evaluation items: judge получает checks/evidence
   и текущий report без worker procedure. Полные инструкции CLI для PM не менять.
   Явно оставить задачу judge: оценить предоставленный пакет, а не выдать собственную
   аттестацию происхождения недоступной ему переписки.
2. Только PM-DRAFT-02/03: не наследовать covered предыдущего отчёта. Применить это
   одинаково при сборке до модели и при повторной проверке state/fingerprint,
   включая technical-error snapshot. Историю не удалять; reader, остальные роли,
   phase01 coverage и legacy-вызовы сохранить.
3. Выполнить два изменения последовательно с отдельными регрессиями, чтобы не
   смешивать причинные факторы. Версионировать изменённый evaluator contract;
   frozen v12 и старые исполнения продолжать читать/валидировать прежним способом.
4. Регрессии: текущий FULL отсутствует после старого covered; новая revision/hash;
   ложный старый covered позднее опровергнут; корректный полный пакет; controls133/153/163;
   неизменность других ролей/legacy; current owner/revision guards до/после модели.
   Моки доказывают механику, не качество оценки. После них — ограниченная заранее
   размеченная проверка модели, затем два PM-сценария до Backlog / Ready без Analyst.

Пакет устраняет доказанное противоречие входа, **не гарантирует устранения false PASS**.
Не нужны новая модель-проверяющий, resolver, БД/API, обход consent, автоматический
PASS или переписывание valid verdict. Диагноз завершён; исправление и выпуск PM — нет.
