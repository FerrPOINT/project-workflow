# Приёмка Workflow через CLI

## Текущий Релиз

Контракт: [архитектура](docs/architecture.md) и [CLI/API](docs/configured-cli-v1.md).
Ниже перечислены обязательные границы; исторический успешный прогон их не закрывает.

| Граница | Проверка |
| --- | --- |
| Standalone | Свежая PostgreSQL без Fleet/Auth/Tracker; собственные workflow и namespace; явный `step --start`, PARTIAL, исправление, завершение, history и рестарт |
| Platform | Прежний PM; полный запрос и скудная идея с замечанием и новой редакцией; отдельное owner confirmation; самостоятельный Workflow completion; раздельные readbacks стадии и статуса Tracker |
| Передача роли | После Workflow PM приложение/Tracker передаёт задачу на Analysis; начало работы Analyst и установка InProgress проверяются отдельно. Ни PASS Advisor, ни complete=true сами не являются переходом Tracker |
| Один Advisor | Новый отчёт вызывает модель один раз; форматный/транспортный отказ не продвигает фазу; readback принятой операции вызывает модель ноль раз |
| Состояние | Изоляция задач, фаз, режимов и циклов; отзыв covered; конфликт критериев/версии; конкуренция; потерянный ответ и сохранение истории |
| Допуск | Standalone только loopback, platform без Auth не стартует; платформенная БД не допускается в standalone; чужие данные закрыты |
| Ожидание | Model read 1200 секунд, connect 30, CLI read 1500; искусственная задержка проверяет передачу бюджета без двадцатиминутного ожидания |
| Выпуск | Native/PostgreSQL/coverage 94%/lint/types, упаковка и preserving update; затронутые экраны в Chromium/Firefox/WebKit |

Зафиксированный набор квалификации модели: 17 случаев по два образца и ещё два
для 189, максимум 36 HTTP-вызовов без автоматических повторов. Первое расхождение
останавливает выпуск. Все ответы сохраняются; неизменённую серию не повторять
до удобного PASS. Это описание набора, не разрешение новой серии при неизменных
входах: применимость прежних результатов и согласованный остаток вызовов
проверяются до запуска. Текущий результат и невыполненные gates — в CHANGELOG.

## Прямой Платформенный Прогон

Действующий ручной сценарий: [инструкция](manual/file-sandbox/README.md).
Его запускают отдельно от обычных тестов, только по явному поручению.

Следующий живой прогон выполняется в
[строгом режиме с нового пользовательского запроса](manual/file-sandbox/STRICT_USER_REQUEST.md):
создание задачи и назначения входит в проверку; вмешательства после старта
исключены. Подготовка стенда не считается прохождением этого теста.

[Прогон 2026-10-28](docs/testing/cli-live-20261028.md): все три фазы PM приняты
настоящим advisor через CLI, Tracker подтвердил завершение в `Backlog / Ready`.
Общая приёмка остаётся частичной: остальные семь режимов ещё не запускались.

## Живой прогон

Оператор сверяет версии API и CLI, настраивает доступ через настоящие Auth и
Tracker выбранной установки, создаёт тестовые задания и действующие назначения.
Файловые сценарии регистрируются как обычные воркфлоу соответствующих профессий.
Подготовка не выставляет задаче принятую фазу или оценку.

Агент работает только так:

1. `project-workflow --json step --task <key>` — получить фактическую инструкцию.
2. Выполнить работу, проверить файлы и написать свой отчёт о результате.
3. Отправить отчёт через `step --report -`, передав стабильный ключ операции
   и версию из ответа CLI. Выполнить замечания настоящего advisor.
4. Прочитать полную историю через `history`. При неизвестном результате запроса
   сначала прочитать исходную операцию, не повторяя её с изменённым телом.

Проверяются все семь профессий и восемь режимов, включая Developer initial/rework.
Для PM сохраняется подтверждение точной редакции владельцем. Успех подтверждают
сохранённая CLI-история и независимая проверка файлов. Содержимое запросов и
ответов сохраняют без секретов; историю фактической задачи открывают через Codex IAB.

Прямые вызовы engine/application services и запись фаз в БД эту проверку не
заменяют. Нельзя отвечать вместо advisor, редактировать сохранённые решения или
подменять Auth, Tracker и CLI. Замечание модели, противоречащее фактам, сохраняют
как дефект. Незавершённые режимы и недоступные проверки явно отмечают.

## Автоматические проверки

Обязательные команды и пороги: [quality gate](docs/quality-gate.md).
Unit-тесты используют контролируемые внешние ответы. PostgreSQL integration
проверяет хранение, миграции, права и конфликты на одноразовой БД. Ни один из этих
результатов не доказывает работу реального advisor и агента через установленный CLI.

Сам recorder проверяется отдельно: `python manual/file-sandbox/cli_checks.py`.
Этот запуск не выполняет пользовательскую работу и не вызывает модель.

## Исторические результаты

[Прежний регламент](docs/history/live-test-plan-legacy.md) относится к удалённым
контрактам. Старый `manual/file-sandbox/run.py` сохранён как явно названная
`engine-diagnostic`; прежняя команда `run --live` отклоняется. Даже с настоящей
моделью его результат остаётся диагностикой ядра, без доказательства CLI-пути.
