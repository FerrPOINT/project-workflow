# Прямой тест Workflow через CLI

Codex сам выполняет роль агента: читает `project-workflow step`, выполняет
файловое задание и отправляет фактический отчёт настоящему advisor.
Fleet не исполняет задание, сообщения в его чат не отправляются.
Это отдельная граница от [сценария с первого запроса](STRICT_USER_REQUEST.md).

## Подготовка

До первого агентского шага подготовить настоящие Auth/Tracker, постоянную
конфигурацию CLI, действительное тестовое назначение, отдельные исходные файлы
и тестовые определения. Текущий PM API требует подтверждённую редакцию
требований перед финальным отчётом. В техническом тесте её допускается заранее
подготовить как явно обозначенную операторскую фикстуру. Такая фикстура
**не является** проверкой решения настоящего пользователя. Не выдавать её
за полученное во время прогона согласование бизнес-требований.

```sh
python manual/file-sandbox/cli.py prepare --direct --root .local/direct-cli-001
```

Команда создаёт только исходные файлы и каталог с отдельными ключами
`file-sandbox-direct-v1:<profession>`. Прежние воркфлоу и история сохраняются.
Штатный `register_catalog.py` принимает каталог с проверкой SHA256, семи
профессий, восьми режимов и идентичности повтора. Смешанные каталоги запрещены.
Регистрацию выполняет оператор до теста по порядку из [README](README.md).

После подготовки зафиксировать hash каталога, recorder, проверяющего модуля,
конфигурации CLI, исходных файлов и установленных образов. Предпосылки доступа
и согласования хранить отдельно. Их поведение не включать в проверку Workflow.

## Прогон

После первого шага разрешены штатные `step`/`history`, работа с файлами задания
и запись неизменённых результатов CLI. Не менять систему, права, модель,
каталог и проверяющий код. Не проставлять фазы и оценки вручную.

1. Получить фазу через установленный CLI.
2. Выполнить полученные инструкции; Python запускать с `-B`.
3. Перед изменениями один раз честно сообщить, что они ещё не выполнены.
4. Прочитать настоящий ответ advisor. Выполнить замечания либо объяснить
   противоречие исходному контракту фактами. Лишнее условие сохранить как дефект;
   не переписывать критерии ради PASS.
5. Отправлять фактические отчёты через stdin со стабильным ключом и версией CLI.
6. После каждой сохранённой операции читать её исходный ключ через CLI history.
7. В конце получить полную историю и проверить реальные файлы независимым модулем.

Recorder запускает установленный CLI отдельным процессом. Он не выбирает verdict
и не вызывает движок внутри Python-процесса.

```sh
python manual/file-sandbox/cli.py step --root .local/direct-cli-001 --case project_manager-draft --task ACTUAL_TASK_KEY
python manual/file-sandbox/cli.py history --root .local/direct-cli-001 --case project_manager-draft --task ACTUAL_TASK_KEY
python manual/file-sandbox/cli.py finish --root .local/direct-cli-001 --case project_manager-draft
```

Параметры передачи отчётов описаны в README. У recorder нет параметра `--n`;
обычный `history` читает страницу CLI, `--before-history-id` позволяет дочитать
остальные. Перед `finish` нужно полное чтение истории, а не только одной операции.

`finish --case ...` создаёт `result-<case>.json` со scope `single-case` и списком
непроверенных режимов. Общий `finish` без `--case` по-прежнему требует все восемь.
Один завершённый режим не объявлять полной приёмкой.

## Результат

Успех означает три принятые фазы, `complete=true`, совпадающие операции и историю,
проверенные создание/изменение/удаление файлов и независимую арифметику.
Ошибки advisor учитывать отдельно даже при последующем завершении.
Этот результат не доказывает защиту от любого ложного отчёта агента.

Прямой тест заканчивается на сохранённом результате Workflow. Чаты Fleet,
native runtime, создание задачи из первого сообщения, настоящее решение владельца
и бизнес-переход Tracker в Backlog / Ready этим прогоном не проверяются.
