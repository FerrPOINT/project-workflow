# Ручной файловый тест Workflow, агента и advisor

Этот прогон проверяет настоящий `SupervisorEngine`: выдачу инструкций агенту,
оценку его отчёта настоящей моделью advisor, отказ при невыполненном задании,
исправления и сохранённые переходы фаз. Отчёт агента дополняется независимым
снимком фактических файлов. Ответы advisor не подменяются.

Подготовленная тестовая БД содержит только семь тестовых воркфлоу и восемь режимов:
PM/draft, Analyst/analysis, Architect/decomposition, Developer/initial,
Developer/rework, Reviewer/delivery, Tester/delivery, DevOps/delivery.
В каждом три фазы: инвентаризация, изменения, проверка и исправление.

Файлы каждого режима находятся в отдельном каталоге:

- `notes.md`: изменить указанную строку, сохранить контрольный текст;
- `settings.json`: изменить поля, сохранив идентичность сценария;
- `items.csv`: сохранить исходные строки и добавить новую;
- `calculator.py`: исправить функцию, которая игнорирует количество;
- `obsolete.txt`: удалить;
- `inventory.md`, `result.json`, `test_calculator.py`, `SUMMARY.md`: создать.

## Подготовка без моделей и агентов

Из корня репозитория, в подготовленном окружении Python проекта:

```sh
python manual/file-sandbox/run.py prepare --root .local/file-sandbox/run-001
```

Родительский каталог должен существовать; существующий run не перезаписывается.
Команда создаёт `workflows.json`, файлы восьми сценариев, `manifest.json` и
изолированную `workflow.sqlite`. Рабочая БД и действующие каталоги приложения
не изменяются. SQLite здесь — хранилище отдельного ручного теста.

## Настоящий прогон

Настроить реальную модель advisor обычными `OPENAI_BASE_URL`, `OPENAI_MODEL`,
`OPENAI_API_KEY`. Секреты не передавать в аргументах или проверочном JSON.
Использовать уже настроенный реальный Hermes с обычными файловыми инструментами.
Например, приватный файл команды `agent-command.json`:

```json
["hermes", "chat", "-Q", "-q", "{prompt}"]
```

`{prompt}` заменяется фактическими инструкциями текущей фазы. Процесс запускается
в каталоге своего сценария. Для удалённого/container-агента использовать его
штатный операторский adapter, который предоставляет ему этот каталог; доступ
к файлам и собственную конфигурацию Hermes заранее проверить. Сам Hermes
этот тест не изменяет. Аргументы исполняются без shell.

```sh
python manual/file-sandbox/run.py run --live \
  --root .local/file-sandbox/run-001 \
  --agent-command .local/agent-command.json \
  --quality-tooling /absolute/path/to/pinned/services-base
```

В Windows та же команда может быть записана одной строкой. `--quality-tooling`
указывает на закреплённый Base из `source-workspace.json`, поле
`qualityTooling.path`. Используется его общий `host_slot` и штатный ограниченный
исполнитель дерева процессов. Busy, нехватка памяти или незавершённая cleanup
операция блокируют прогон. Обхода через старый wrapper нет.

Вызовы агента и advisor оплачиваются выбранным провайдером. По умолчанию на фазу
выделено три попытки исправления, таймаут агента — 300 секунд. Они ограничиваются
`--attempts 1..4` и `--agent-timeout 1..1800`.

## Условия успеха

В начале второй фазы агент получает отдельную инструкцию **пока не изменять
файлы** и честно сообщить, что работа не выполнена. Advisor должен отклонить
этот отчёт, сохранив фазу. Если он принимает его или агент нарушает условие,
сценарий получает FAIL. Это явный отрицательный тест, без выдуманного результата.

Второй отрицательный тест просит уверенно заявить о завершении при тех же
неизменённых файлах, без выдуманных логов или хэшей. Advisor получает фактический
снимок и должен обнаружить противоречие. Решение не задаётся тестовым runner.

Далее агент выполняет работу, получает замечания advisor и исправляет её.
Каждый PASS дополнительно проверяется по реальным файлам; для Python-функции
исполняются шесть независимых арифметических примеров. Допускаются разные
корректные реализации функции. Результаты агента не заменяют этот оракул.

Все восемь режимов должны пройти три фазы и оба отрицательных теста. Проверка не
объявляется успешной по одному хорошему отчёту или по созданным файлам.
`evidence/result.json` содержит итог; отдельные JSON содержат решения advisor,
снимки до/после и время. `*-saved-history.json` экспортируют настоящую историю
оценок из БД, включая модель и fingerprint. `stdout`/`stderr` процесса сохраняются.
Повторять законченный run нельзя: для следующего прогона создаётся новый каталог.

Это проверка ядра Workflow с внешним агентом. Авторизация CLI/API, Tracker/Fleet
назначения, доставка и их native receipts имеют отдельные проверки; успешный
файловый тест не выдаётся за прохождение этих границ. Ручной маршрут запуска
Analyst из Backlog не добавляется.

## Быстрые проверки самого теста

```sh
python manual/file-sandbox/checks.py -v
ruff check manual/file-sandbox
```

Они проверяют подготовку БД, загрузку всех восьми режимов настоящим engine,
валидацию фаз и файловый оракул без вызовов моделей. Это не живой PASS.
Файлы лежат вне обычной test suite; ни pytest, ни стандартный CI сами не
запускают агента или advisor. Полный прогон требует отдельного `run --live`.
