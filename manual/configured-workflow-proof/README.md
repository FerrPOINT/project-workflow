# Ручная приёмка общего Workflow в PDLC1

Сценарий запускается только оператором, вне pytest/CI и обычного полного gate.
Он дополняет PostgreSQL, контракты и упакованные CLI, не заменяя их. Наличие этого
сценария не означает, что он выполнен или принят.

## Подготовка

Использовать только PDLC1 и отдельные тестовые Task/Project/репозиторий/чат.
До переключения подтвердить завершение старых native attempts, сохранить данные,
ledger, предыдущие образы и проверяемый rollback. Установить точный проверенный
cohort штатным Base-механизмом. Проверить реальные обслуживаемые SHA, CLI и
текущие права всех семи служебных identities. Не менять Hermes и соседние группы.

Рабочий тестовый репозиторий должен быть доступен штатному Forge pipeline и
иметь разрешённое место установки проверочного HTTP-сервиса в PDLC1. Координаты
берутся из действительных source/deployment receipts. Если такого назначения
нет, приёмка блокируется; создавать обходной docker run или постороннюю группу нельзя.

## Бизнес-задание владельца

Сделать HTTP API расчёта доставки: `GET /health` возвращает JSON `status=ok`;
`POST /quote` принимает закрытый JSON с полями `subtotal`, `weight_grams`, `zone`.
`subtotal` — строка неотрицательной суммы с двумя десятичными знаками;
`weight_grams` — целое число от1 до20000, boolean не считается числом;
`zone` — `local` либо `remote`. Некорректный запрос возвращает HTTP400 с JSON.

Базовая доставка local15.00 RUB, remote25.00 RUB. Первые1000г включены;
каждая следующая начатая1000г добавляет5.00 RUB. При local и subtotal≥1000.00
базовая стоимость равна нулю, весовая доплата сохраняется. Remote не бывает
бесплатным. Ответ содержит только `shipping`, `total`, `currency`: суммы —
строки с двумя знаками, currency=`RUB`. Деньги вычисляются точно без округления
промежуточных значений через binary float. Нужны тесты границ и некорректных
запросов, инструкции запуска и действительная установка с проверкой здоровья.

## Проход профессий

1. Отправить задание настоящему PM через обычный Fleet-чат. Агент сам читает
   Workflow, полную дискуссию и сохраняет требования. Владелец подтверждает
   конкретную сохранённую редакцию/hash. PM выполняет свои команды сам и
   заканчивает в Backlog/Ready. Подтвердить отсутствие автоматического Analyst.
2. Через штатное разрешённое назначение Tracker/Fleet запустить Analyst, затем
   Architect, Developer initial, Reviewer, Tester и DevOps. Оператор не пишет код,
   фазовые отчёты, evidence или итоговые комментарии за агента.
3. Сохранить настоящие назначения, все страницы обсуждения/истории, выполненные
   агентом команды, отчёты/оценки, final comments, source/CI/deployment receipts и
   native terminal. Сопоставить каждое действие с задачей, профессией и редакцией.
4. Проверить Developer rework и повторные Review/Testing на реальном замечании
   Reviewer/Tester либо обоснованном техническом запросе к кандидату. Оператор
   не подменяет verdict и не вносит дефект сам. Если Rework не был исполнен,
   отметить NOT EXERCISED и оставить этот критерий открытым.
5. Отдельно проверить критический бизнес-возврат: настоящее противоречие,
   выбранный `context.critical_review`, новая полная редакция и точный consent,
   прежняя история, атомарное разрешение blocker и Backlog/Ready без Analyst.
   Не принимать synthetic unit receipts за доказательство такого прохода.

## Независимый бизнес-оракул

Проверять реальный установленный сервис из deployment receipt. SHA сначала
сверить с Forge, образом и обслуживаемыми ресурсами; аргумент CLI сам происхождение
не доказывает. Оракул хранится у оператора вне рабочего репозитория агентов,
не читает их код, не создаёт задачу и не отправляет Workflow/Tracker команды.

```sh
python manual/configured-workflow-proof/oracle.py --base-url http://localhost:PORT --candidate-sha FULL_SHA --output .local/proof/business-oracle.json
```

Каталог evidence создать заранее; существующий результат не перезаписывается.
Оракул проверяет19 HTTP-сценариев, включая границы цены/веса, округление,
недопустимые типы и закрытую схему. Зелёный оракул доказывает только бизнес-поведение.

## Остальные обязательные доказательства

- Несколько сообщений не создают Workflow request/token/bootstrap-файлы.
- Повтор команды возвращает исходный результат; изменённый payload конфликтует.
  При неизвестном HTTP-результате агент читает исходную операцию.
- Чужая задача, отозванные проектные права, старое назначение и версия не пишутся.
- Прочитаны все страницы обсуждения; итоговый комментарий существует до передачи.
  Изменение/удаление комментария блокирует новый handoff.
- После restart читается прежняя история с неизменными ID и продолжается текущая
  незавершённая фаза, включая задачу, созданную до перехода.
- UI проверяется только в Codex IAB; сохранить скриншоты и фактический URL.

В итоговой таблице для каждого из8 режимов указать task/assignment/Workflow
execution, phase/history IDs, исходный/финальный SHA, проверку комментария,
настоящий terminal и результат оракула. Незавершённые/незапущенные проверки не
объявлять PASS. Приёмка кандидата предшествует merge и итоговому readback.
